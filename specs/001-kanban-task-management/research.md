# Research & Decisions: Kanban Task Management

Phase 0 output. Each decision resolves a Technical Context unknown or a technology choice.

## D1. Language & runtime: C# 14 / .NET 10 LTS

- **Decision**: Target .NET 10 LTS (C# 14).
- **Rationale**: .NET 10 LTS is the current long-term-support release and the required runtime
  for .NET Aspire 13. LTS aligns with a security-first posture (supported security patches).
- **Alternatives considered**: .NET 8 LTS (older LTS, still supported but predates Aspire 13
  features); .NET 9 STS (shorter support window — rejected for security reasons).

## D2. Orchestration & hosting: .NET Aspire 13

- **Decision**: Use .NET Aspire 13 (`AppHost` + `ServiceDefaults`) to compose and run the two
  services and PostgreSQL locally, with the dashboard for logs/traces/metrics.
- **Rationale**: Aspire is the Microsoft-native cloud-native stack that gives service discovery,
  configuration injection (connection strings), health checks, and OpenTelemetry out of the box,
  directly supporting the constitution's microservices and observability expectations.
- **Alternatives considered**: docker-compose alone (no built-in service discovery/telemetry);
  manual K8s manifests (heavyweight for a small-team MVP).

## D3. Storage: PostgreSQL via EF Core 10 + Npgsql

- **Decision**: PostgreSQL as the single relational store, accessed only by `Taskify.Api`
  through EF Core 10 with the Npgsql provider and code-first migrations.
- **Rationale**: Relational integrity fits the entities (projects → tasks → comments,
  assignees); Postgres is the plan's stated requirement and Aspire's `AddPostgres` resource
  handles local provisioning and connection-string injection.
- **Alternatives considered**: SQL Server (not requested); SQLite (rejected — not a production
  microservices store and conflicts with "Postgres" requirement).

## D4. Backend API style: ASP.NET Core Minimal APIs

- **Decision**: Implement the REST API with ASP.NET Core Minimal APIs (route groups per resource),
  with OpenAPI/Swagger for contract documentation.
- **Rationale**: Minimal APIs are the modern, low-ceremony way to expose documented REST
  endpoints and map cleanly to the contract-first approach required by the constitution.
- **Alternatives considered**: Controller-based APIs (more boilerplate, no added value here).

## D5. Input validation: FluentValidation

- **Decision**: Enforce all validation server-side with FluentValidation validators bound at the
  API boundary; client-side validation is UX-only.
- **Rationale**: Constitution Principle II makes server-side validation non-negotiable;
  FluentValidation gives testable, centralized rules (required, trimmed, max length, enum
  membership) and fails closed on invalid input.
- **Alternatives considered**: Data annotations alone (harder to unit test and centralize);
  manual checks in endpoints (error-prone, violates single-responsibility).

## D6. Frontend: Blazor Server (Interactive Server rendering)

- **Decision**: Build the UI as a Blazor Server app (Interactive Server) with drag-and-drop
  Kanban columns and real-time updates over SignalR.
- **Rationale**: Blazor Server is the stated requirement; its SignalR circuit is the natural
  transport for real-time board/notification updates. Server rendering keeps business logic off
  the client and aligns with the security-first posture.
- **Alternatives considered**: Blazor WebAssembly (client-side, requires a public API surface
  and more client trust — rejected for phase 1); a separate JS SPA (out of the .NET stack).

## D7. Real-time updates: SignalR hub in `Taskify.Web`

- **Decision**: Host a SignalR hub in `Taskify.Web`. After any successful mutation (create,
  move, assign, comment), the Web broadcasts the updated state/notifications to all connected
  clients. Notifications generated by the API are included in mutation responses and broadcast.
- **Rationale**: Single-instance broadcast is sufficient for a 5-user MVP and avoids introducing
  a message broker. This keeps the API a clean request/response system of record.
- **Alternatives considered**: A dedicated message broker (Redis pub/sub or Aspire eventing) —
  deferred: only needed for multi-instance scale or API-originated events from outside the Web.
- **Note**: If the API must push events to clients independent of Web-initiated mutations later,
  introduce a broker or SignalR backplane in a future phase.

## D8. Microservices boundary: `Taskify.Api` + `Taskify.Web`

- **Decision**: Two services. `Taskify.Api` owns all data (the only service with DB access) and
  exposes projects, tasks, notifications, and users. `Taskify.Web` renders the UI and calls the
  API over REST via a typed HTTP client.
- **Rationale**: This decomposition satisfies the constitution's "independently deployable
  services" and "no shared database" rules with the smallest meaningful boundary.
- **Alternatives considered**: A separate notifications microservice (extractable later; overkill
  for the MVP); a single monolith (violates the microservices constitution principle).

## D9. Identity: client-selected user, no login (phase 1)

- **Decision**: The active user is selected in the UI and sent to the API as an
  `X-Taskify-User-Id` header on mutating requests; the API attributes every action (FR-014).
- **Rationale**: This is the explicit phase-1 "no login" requirement. It is recorded as a
  constitution deviation (authentication/authorization deferred).
- **Alternatives considered**: Real auth (deferred); a global "acting user" flag (less explicit
  than a per-request header).
- **Security note**: This is not authentication and must be replaced before any multi-tenant or
  public deployment.

## D10. Notifications: server-generated, read via REST

- **Decision**: The API creates `Notification` records on key events — task assigned to a user,
  task status changed, comment added on a task the user is involved with — and exposes them via
  `GET /api/notifications`. Marking read is via `PATCH`. The Web surfaces them and broadcasts
  new ones over SignalR.
- **Rationale**: Satisfies the plan input's "notifications REST API" while keeping the API the
  single source of truth.
- **Alternatives considered**: Client-generated notifications (inconsistent); push-only without
  persistence (loses history on reconnect — rejected).

## D11. Testing strategy

- **Decision**: xUnit for API unit/integration (validation rules + endpoint behavior via
  WebApplicationFactory with a test Postgres or in-memory provider), bUnit for Blazor component
  tests (board render, drag/drop handling, empty states), and Aspire.Hosting.Testing for an
  end-to-end smoke test.
- **Rationale**: The constitution requires automated tests for security-relevant and validation
  paths; these three layers cover unit, component, and integration levels.
- **Alternatives considered**: Playwright UI tests (adds browser dependency; can be added later).

## D12. Drag-and-drop

- **Decision**: Implement drag-and-drop with the HTML5 Drag-and-Drop API wired through Blazor
  event handlers, with keyboard-accessible move buttons as a fallback (accessibility).
- **Rationale**: Avoids a third-party JS interop dependency for the MVP while meeting the
  drag-and-drop requirement; keyboard fallback keeps the board usable without a pointer.
- **Alternatives considered**: Blazor Sortable/JS interop libraries (richer UX, more surface —
  can be added later).
